# Бизнес-правила

## Пользователи

- Основной логин пользователя — `username`.
- `email` используется как вспомогательное контактное поле и не участвует в основной аутентификации.
- Email пользователя необязателен.
- Если email указан, он должен быть уникальным.
- API-регистрация требует `email` и возвращает JWT pair после создания пользователя.
- Телефон пользователя необязателен.
- Web-аутентификация использует Django sessions.
- API-аутентификация использует JWT.
- Пользователь должен видеть только собственные заказы и профильные данные.
- После успешного web-входа гостевая session-корзина объединяется с DB-корзиной пользователя.

## Каталог

### Категории

- `slug` категории уникален.
- Неактивные категории не отображаются в публичном каталоге.
- Удалённые через soft delete категории не отображаются в публичном каталоге.
- Вложенность категорий допускается через `parent`.

### Товары

- `slug` товара уникален.
- `sku` товара уникален.
- Цена товара не может быть отрицательной.
- Старая цена, если используется, не может быть отрицательной.
- Остаток товара не может быть отрицательным.
- Товар доступен к покупке, если он активен и остаток больше нуля.
- Неактивные товары не отображаются в публичном каталоге.
- Удалённые через soft delete товары не отображаются в публичном каталоге.

### Публичный каталог

- Главная страница показывает только товары из публичного queryset каталога.
- Список товаров показывает только активные неудалённые товары.
- Товары из неактивных или soft-deleted категорий не отображаются.
- Поиск работает по названию, описанию и SKU.
- Фильтр категории принимает `slug` активной категории.
- Фильтр цены поддерживает нижнюю и верхнюю границы.
- Некорректные значения цены в GET-параметрах игнорируются, а не ломают страницу.
- Сортировка поддерживает `newest`, `price_asc`, `price_desc`, `popular`.
- Сортировка `popular` на текущем этапе считается по количеству связанных позиций заказа.
- Детальная страница товара доступна по URL `/products/<slug>/`.
- Детальная страница использует те же правила публичной видимости, что и список товаров.
- Неактивный товар, soft-deleted товар или товар из скрытой категории должен возвращать 404.
- На детальной странице отображаются название, описание, цена, остаток и изображение из `ProductImage`.
- Если у товара нет изображений, страница должна корректно показывать состояние `Изображение отсутствует`.
- Если товар есть в наличии, детальная страница показывает POST-форму `Добавить в корзину`.
- Если `stock_quantity = 0`, отображается состояние `Нет в наличии`.
- На детальной странице отображаются только опубликованные отзывы.
- Средний рейтинг и количество отзывов считаются только по опубликованным отзывам.
- Форма создания отзыва может отображаться на детальной странице, если пользователь авторизован и имеет подтверждённую покупку товара.
- Похожие товары выбираются из той же активной категории, исключают текущий товар и ограничены 3 позициями.
- Товары с `stock_quantity = 0` могут отображаться в похожих товарах, но должны иметь состояние `Нет в наличии`.

### Soft delete

- Soft delete используется только для `catalog.Category` и `catalog.Product`.
- `TimeStampedModel` не содержит поля soft delete.
- Заказы, позиции заказа, платежи и отзывы не используют soft delete на текущем этапе.
- Для публичного каталога selectors должны исключать записи с `is_deleted=True`.
- Подключение soft delete к другим моделям требует пересмотра ADR `0006-soft-delete.md`.

### Изображения товаров

- У товара может быть несколько изображений.
- Главное изображение определяется через `ProductImage.is_main`.
- Если главное изображение не задано, допускается выбрать первое изображение по `sort_order` и `id`.
- Изображения нельзя подбирать по `slug` товара.
- `src/prepare/` не используется напрямую как источник runtime-изображений.
- Альтернативный текст изображения нужен для доступности и SEO.

## Корзина

Корзина использует гибридный подход:

- неавторизованный пользователь хранит корзину в session;
- авторизованный пользователь хранит корзину в БД;
- после входа или регистрации session-cart объединяется с DB-корзиной пользователя.

Web-маршруты корзины:

- `GET /cart/` показывает текущую корзину;
- `POST /cart/add/<product_id>/` добавляет товар;
- `POST /cart/update/<product_id>/` заменяет количество;
- `POST /cart/remove/<product_id>/` удаляет позицию;
- `POST /cart/clear/` очищает корзину.

Общие правила корзины:

- Нельзя добавить неактивный товар.
- Нельзя добавить товар без остатка.
- Количество позиции должно быть больше нуля.
- Количество позиции не должно превышать доступный остаток.
- В одной позиции корзины может быть не больше `99` единиц товара.
- Нельзя оформить пустую корзину.
- Checkout доступен только авторизованному пользователю.
- Гостевой checkout на текущем MVP не реализуется.
- Итоговая сумма корзины считается из цены товара и количества.
- Корзина не хранит цену товара, название товара, скидку, остаток или итоговую сумму как источник истины.
- Цена, активность и остаток всегда берутся из актуального `Product`.
- Корзина не резервирует товар на складе.
- При логине количества из session-cart и DB-cart объединяются с ограничением по остатку и системному лимиту.
- `add` увеличивает количество существующей позиции.
- `update` заменяет количество существующей позиции.
- Пользовательская операция с превышением остатка или лимита возвращает ошибку и не меняет корзину.
- Битые `product_id`, soft-deleted товары, неактивные товары и товары из скрытых категорий удаляются при нормализации корзины.
- Товар с `stock_quantity = 0` остаётся видимым в корзине, но блокирует checkout.
- Если количество в корзине стало больше текущего остатка, оно не обрезается silently: пользователь должен явно изменить количество.

API-корзина:

- Требует JWT-аутентификацию.
- Работает только с DB-корзиной авторизованного пользователя.
- Не использует browser session и не выполняет merge гостевой корзины.
- После успешных операций возвращает актуальный snapshot корзины.

## Заказы

- Заказ создаётся из корзины.
- Заказ создаётся только для авторизованного пользователя.
- Заказ принадлежит пользователю через обязательное поле `Order.user`.
- Заказ хранит snapshot контактных данных и адреса доставки.
- Итоговая сумма заказа не может быть отрицательной.
- Создание заказа должно быть атомарным.
- При checkout нужно повторно проверить остатки товаров.
- При checkout нужно фиксировать цену товара в `OrderItem.price`.
- При checkout нужно фиксировать название товара в `OrderItem.product_name`.
- Checkout работает по правилу all-or-nothing: если хотя бы одна позиция недоступна, заказ не создаётся.
- Checkout не уменьшает количество автоматически и не создаёт частичный заказ.
- Товары при checkout блокируются через `select_for_update()` в стабильном порядке.
- Checkout создаёт заказ и платёж с результатом из `apps.payment_emulator`.
- При результате `succeeded` заказ получает статус `paid`, платёж получает статус `succeeded`, остатки товаров уменьшаются, корзина очищается.
- При результате `failed` заказ остаётся в статусе `new`, платёж получает статус `failed`, остатки не уменьшаются, корзина сохраняется.
- При результате `cancelled` заказ остаётся в статусе `new`, платёж получает статус `cancelled`, остатки не уменьшаются, корзина сохраняется.
- При результате `pending` заказ остаётся в статусе `new`, платёж получает статус `pending`, остатки не уменьшаются, корзина сохраняется до финального решения оплаты.
- Дефолтные веса эмулятора оплаты: `succeeded=7`, `failed=1`, `cancelled=1`, `pending=1`.
- Контактные данные checkout берутся из формы и сохраняются как snapshot в заказе.
- После создания заказа checkout отправляет email покупателю и администраторам.
- Email-уведомления являются best-effort: ошибка отправки логируется, но не откатывает созданный заказ и платёж.
- Письма содержат номер заказа, статус заказа, статус оплаты, сумму, список товаров и адрес доставки.

API checkout:

- Требует JWT-аутентификацию.
- Создаёт заказ только из текущей API-корзины пользователя.
- Не принимает список позиций заказа напрямую.
- Использует те же правила проверки остатков и атомарного создания заказа, что web checkout.
- Использует те же email-уведомления, что web checkout.

API compatibility:

- Основные Product API маршруты по `slug` сохраняются.
- Compatibility route `GET /api/products/<id>/` возвращает тот же публичный товар по внутреннему id.
- Compatibility route `POST /api/users/login/` является alias для получения JWT pair.
- Compatibility `GET/POST/PATCH/DELETE /api/cart/` работает поверх той же DB-корзины и тех же cart services.
- Compatibility routes не должны дублировать бизнес-логику отдельно от основных endpoint'ов.

Статусы заказа:

- `new` — создан;
- `paid` — оплачен;
- `processing` — в обработке;
- `shipped` — отправлен;
- `completed` — завершён;
- `cancelled` — отменён.

## Позиции заказа

- Позиция заказа связана с заказом и товаром.
- Цена позиции является snapshot цены на момент оформления.
- Название товара является snapshot названия на момент оформления.
- Количество должно быть больше нуля.
- Цена не может быть отрицательной.

## Отзывы

- Отзыв принадлежит пользователю и товару.
- Один пользователь может оставить только один отзыв на один товар.
- Рейтинг должен быть от 1 до 5.
- Отзыв проходит модерацию.
- Новый отзыв создаётся в статусе `pending`.
- Публично отображаются только опубликованные отзывы.
- Создать отзыв может только авторизованный пользователь с подтверждённой покупкой товара.
- Подтверждённой покупкой считается заказ текущего пользователя с нужным товаром в статусе `paid`, `processing`, `shipped` или `completed`.
- Заказы в статусах `new` и `cancelled` не дают право оставить отзыв.
- На этапе 11 право оставить отзыв проверяется через `Order` и `OrderItem`; `Payment` напрямую не проверяется.
- При успешном создании пользовательского отзыва выставляется `is_verified_purchase=True`.
- Форма создания отзыва может отображаться на `/products/<slug>/`, но POST-запрос обрабатывает приложение `reviews`.
- Канонический web-маршрут создания отзыва на товар: `POST /reviews/products/<slug>/add/`.
- `catalog` не должен напрямую создавать `Review`.

Review API:

- `GET /api/products/<slug>/reviews/` публично возвращает только опубликованные отзывы.
- `POST /api/products/<slug>/reviews/` требует JWT.
- Создание отзыва через API использует `reviews.services.create_product_review()`.

Статусы отзыва:

- `draft` — черновик;
- `pending` — на модерации;
- `published` — опубликован;
- `rejected` — отклонён;
- `hidden` — скрыт.

## Оплата

- Платёж связан с заказом.
- Один заказ может иметь несколько платежных записей.
- Новая попытка оплаты создаёт новую запись `Payment`.
- Старые платежи не перезаписываются.
- У заказа не должно быть больше одного актуального успешного платежа.
- Повторная успешная оплата уже оплаченного заказа должна быть запрещена бизнес-логикой.
- Первичный checkout создаёт `Payment` со статусом, который вернул `apps.payment_emulator`, `provider="payment_emulator"` и суммой, равной `Order.total_price`.
- `payments` остаётся владельцем модели `Payment`; `payment_emulator` только симулирует результат провайдера.
- Сумма платежа не может быть отрицательной.
- Платёж не хранит номер банковской карты, CVV и секретные данные платёжного провайдера.
- Внешний идентификатор платежа хранится только для сверки с провайдером.
- Для локального MVP используется эмулятор оплаты без реальной платёжной интеграции.

Статусы платежа:

- `pending` — ожидает оплаты;
- `succeeded` — успешно оплачен;
- `failed` — ошибка оплаты;
- `cancelled` — отменён;
- `refunded` — возвращён.

## Админская аналитика

- Аналитика доступна только через staff-only Django Admin.
- Расчёты аналитики находятся в `apps.common.analytics`, а не в шаблонах или admin views.
- Выручка считается по сумме успешных платежей `Payment.status = succeeded`.
- Количество заказов считается по `Order`.
- Средний чек считается по подтверждённым заказам в статусах `paid`, `processing`, `shipped`, `completed`.
- Количество оплаченных заказов считается по тем же подтверждённым статусам заказа.
- Ожидающие оплаты считаются по `Payment.status = pending`.
- Неуспешные платежи считаются по `Payment.status = failed`.
- Топ товаров по продажам считается по `OrderItem.quantity` для подтверждённых заказов.
- Товары с низким остатком считаются по текущему `Product.stock_quantity <= 5` и не зависят от выбранного периода.
- Отзывы на модерации считаются по `Review.status = pending`.
- Периодный фильтр применяется к временным метрикам и поддерживает `today`, `7d`, `30d`, `all`.

## Доступ

- Гость может смотреть каталог и карточки товаров.
- Гость может собирать корзину в session.
- Гость не может оформить заказ без входа.
- Авторизованный пользователь может оформлять заказ, смотреть профиль и свои заказы.
- Пользователь не может видеть чужие заказы.
- Пользователь не может изменять чужие отзывы.
- Администратор управляет товарами, заказами, отзывами и платежами через admin.
