# ADR 0022: Web-контракт создания отзыва и граница приложения reviews

## Статус

Принят.

## Контекст

В рамках этапа 11 реализуется создание отзывов пользователями. Детальная страница товара уже показывает read-only блок опубликованных отзывов и рейтинг. Форма создания отзыва пока отсутствует.

В модели `Review` уже есть поля:

```text
rating
title
text
status
is_verified_purchase
```

ADR 0011 зафиксировал, что на этапе 7 страница товара показывает только опубликованные отзывы без формы создания. ADR 0021 зафиксировал, что отзыв может оставить только пользователь с подтверждённой покупкой товара.

Нужно определить web-контракт:

- где отображается форма;
- какой POST URL является каноническим;
- какое приложение владеет HTTP-слоем создания отзыва;
- куда перенаправлять пользователя после обработки;
- как не зашить review-логику внутрь `catalog`.

## Решение

Отзывы реализуются как самостоятельный доменный модуль `reviews`.

Первый web-сценарий этапа 11 — создание отзыва на товар. Форма может отображаться на детальной странице товара:

```text
GET /products/<slug>/
```

Но обработчик создания отзыва находится не в `catalog.views`, а в приложении `reviews`.

Канонический POST-маршрут:

```text
POST /reviews/products/<slug>/add/
```

Разделение ответственности:

`catalog`:

- показывает товар;
- показывает опубликованные отзывы;
- показывает форму или информационное сообщение о невозможности оставить отзыв;
- не создаёт `Review` напрямую.

`reviews`:

- принимает POST-запрос создания отзыва;
- валидирует форму;
- вызывает `reviews.services`;
- проверяет право пользователя оставить отзыв;
- создаёт `Review`;
- выставляет `is_verified_purchase`;
- управляет начальным статусом отзыва;
- выполняет redirect после обработки.

## Web-контракт этапа 11

```text
GET  /products/<slug>/              — детальная страница товара с отзывами
POST /reviews/products/<slug>/add/  — создать отзыв на товар
```

После успешного создания отзыва пользователь возвращается на страницу товара:

```text
/products/<slug>/#reviews
```

Если якорь `#reviews` не используется в шаблоне, допустим redirect на:

```text
/products/<slug>/
```

## Поведение формы

Форма создания отзыва может отображаться на странице товара только если:

- пользователь авторизован;
- пользователь имеет подтверждённую покупку товара по ADR 0021;
- пользователь ещё не оставлял отзыв на этот товар;
- товар доступен для публичного просмотра;
- `reviews.services` разрешает создание отзыва.

Если пользователь не авторизован, можно показать сообщение:

```text
Войдите, чтобы оставить отзыв.
```

Если пользователь не покупал товар:

```text
Оставить отзыв могут только покупатели этого товара.
```

Если пользователь уже оставил отзыв:

```text
Вы уже оставили отзыв на этот товар.
```

## Начальный статус нового отзыва

Новый отзыв создаётся со статусом `pending` и не отображается публично до модерации.

После успешной отправки нужно показать сообщение:

```text
Отзыв отправлен и будет опубликован после проверки.
```

## Инварианты реализации

1. Создание отзыва относится к приложению `reviews`.
2. `catalog.views` не должен напрямую создавать `Review`.
3. Форма отзыва может отображаться на странице товара.
4. Канонический POST URL для отзыва на товар: `/reviews/products/<slug>/add/`.
5. Проверка права оставить отзыв выполняется в `reviews.services`.
6. `Review.is_verified_purchase` выставляется в `reviews.services`.
7. На странице товара отображаются только опубликованные отзывы.
8. Один пользователь может оставить только один отзыв на один товар.
9. Новый отзыв создаётся в статусе `pending`.
10. Review-модуль должен оставаться расширяемым для будущих отзывов на другие объекты.

## Ожидаемая структура маршрутов

```python
from django.urls import path

from apps.reviews import views

app_name = "reviews"

urlpatterns = [
    path(
        "reviews/products/<slug:slug>/add/",
        views.ProductReviewCreateView.as_view(),
        name="product_review_add",
    ),
]
```

## Последствия

Плюсы:

- `reviews` остаётся отдельным доменным приложением;
- `catalog` не получает бизнес-логику создания отзывов;
- web-контракт создания отзыва явно зафиксирован;
- текущий сценарий отзыва на товар не блокирует будущие отзывы на заказ или сервис;
- `reviews.views` и `reviews.services` можно тестировать отдельно.

Минусы:

- URL создания отзыва длиннее, чем POST прямо на `/products/<slug>/`;
- `catalog` должен передавать в шаблон состояние формы или уведомления;
- потребуется больше тестов на границу `catalog` и `reviews`.
