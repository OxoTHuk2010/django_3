# ADR 0014: Сервисный слой корзины и граница ответственности view

## Статус

Принято.

## Контекст

ADR 0002 фиксирует гибридное хранение корзины:

- гость использует session-cart;
- авторизованный пользователь использует DB-корзину.

Но ADR 0002 не определяет границу ответственности между HTTP-слоем и бизнес-логикой корзины.

На этапе 8 нужно реализовать добавление, изменение, удаление, очистку, расчёт итогов, нормализацию недоступных товаров и merge session-cart в DB-cart. Если разместить эти правила во views, HTTP-слой начнёт знать внутренний формат корзины и будет дублировать бизнес-логику, которая позже понадобится checkout и API.

Конфликт C012 закрывается этим ADR.

## Решение

Вся бизнес-логика корзины размещается в `apps/cart/services.py`.

Views остаются тонким HTTP-слоем и отвечают только за:

- приём request;
- чтение и базовую валидацию HTTP-формы;
- поиск товара по `product_id`, если это нужно для действия;
- вызов сервисной функции;
- установку messages;
- render или redirect.

Сервисный слой отвечает за:

- выбор storage-механизма: session-cart или DB-cart;
- добавление товара;
- изменение количества;
- удаление товара;
- очистку корзины;
- расчёт итогов;
- нормализацию невалидных позиций;
- merge session-cart в DB-cart;
- возврат snapshot для шаблона.

Публичный контракт service-layer на этапе 8:

- `get_cart_snapshot(request)`;
- `add_to_cart(request, product, quantity)`;
- `update_cart_item(request, product, quantity)`;
- `remove_from_cart(request, product)`;
- `clear_cart(request)`;
- `merge_session_cart_to_user_cart(request, user)`.

Точная форма результата может быть уточнена при реализации, но сервисы должны возвращать структурированный результат, достаточный для messages, шаблонов и тестов.

## Отклонённые варианты

- Разместить всю логику во views: быстрее старт, но нарушает архитектурный принцип проекта и усложняет тестирование.
- Сделать отдельные `SessionCart` и `DbCart`, а выбор оставить view: view будет знать слишком много о способе хранения.
- Дать checkout и API читать session-cart напрямую: приведёт к дублированию правил и разъезду поведения.

## Последствия

Плюсы:

- view не содержит бизнес-правила корзины;
- session-cart и DB-cart получают единый внешний контракт;
- правила можно тестировать отдельно от HTTP;
- checkout и API смогут переиспользовать те же правила;
- внутренний формат session-cart можно менять без переписывания views.

Минусы:

- нужно заранее поддерживать понятную структуру результатов сервисов;
- в `services.py` потребуется аккуратное разделение публичных функций и приватных helper-функций;
- сервисный слой потребует отдельного набора тестов.

## Инварианты реализации

- View не выбирает между session-cart и DB-cart.
- View не считает `total_price`.
- View не нормализует недоступные позиции.
- View не содержит stock validation.
- View не знает внутренний формат session-cart.
- Checkout и будущий API не должны обходить service-layer корзины.

## Требования к тестам

На уровне сервисов нужно покрыть:

- добавление нового товара;
- увеличение количества существующего товара;
- замену количества;
- удаление позиции;
- очистку корзины;
- расчёт итогов;
- нормализацию недоступных товаров;
- merge session-cart в DB-cart;
- ошибку при `quantity < 1`;
- ошибку при превышении остатка;
- ошибку при недоступном товаре.
