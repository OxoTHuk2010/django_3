# ADR-0007: Использование username как основного логина пользователя

## Статус

Принято.

## Контекст

В проекте используется кастомная модель пользователя `users.User`, наследуемая от `AbstractUser`.

Ранее рассматривался вариант использования `email` как основного логина. Это требовало дополнительной проверки пользовательских сценариев:

- создание суперпользователя внутри Docker;
- вход в Django Admin;
- получение JWT-токена;
- уникальность email;
- поведение поля username.

На текущем этапе проекта использование email как основного логина создаёт избыточную сложность и требует дополнительной кастомизации стандартной логики Django.

## Решение

Основным логином пользователя остаётся стандартное поле `username`.

Поле `email` используется как вспомогательное контактное поле и не участвует в основной аутентификации.

Модель `users.User` наследуется от `AbstractUser`.

В модели явно фиксируется:

```python
USERNAME_FIELD = "username"
REQUIRED_FIELDS = []
```

Поле email допускается как необязательное. При необходимости бизнес-логики один email должен принадлежать только одному пользователю.

Рекомендуемая настройка поля:
```python
email = models.EmailField(
    blank=True,
    null=True,
    unique=True,
)
```

### Последствия

Плюсы:

- используется стандартный механизм аутентификации Django;
- упрощается создание суперпользователя;
- упрощается вход в Django Admin;
- упрощается получение JWT-токена;
- уменьшается количество кастомного кода;
- снижается риск ошибок в формах, сериализаторах и тестах.

Минусы:

- пользователь не сможет входить по email без отдельной доработки;
- если в будущем потребуется login by email, понадобится отдельный ADR и изменение логики аутентификации;
- поле email остаётся вспомогательным и не должно использоваться как идентификатор пользователя.
