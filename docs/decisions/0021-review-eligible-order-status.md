# ADR 0021: Право пользователя оставить отзыв после подтверждённой покупки

## Статус

Принят.

## Контекст

В рамках этапа 11 реализуется создание отзывов пользователями. В проекте уже есть модель `Review`, связь отзыва с `user` и `product`, поле `is_verified_purchase`, уникальность пары `user + product`, а также заказы и позиции заказов.

У заказа есть статусы:

```text
new
paid
processing
shipped
completed
cancelled
```

Checkout на текущем этапе создаёт заказ со статусом `paid` и успешный mock-платёж. Перед реализацией `reviews.services.user_can_review_product()` нужно зафиксировать, какие именно заказы подтверждают покупку товара.

## Решение

Пользователь может оставить отзыв, если у него есть хотя бы один заказ с нужным товаром в одном из подтверждённых статусов:

```text
paid
processing
shipped
completed
```

Проверка права на отзыв выполняется через `Order` и `OrderItem`:

- заказ принадлежит текущему пользователю;
- заказ содержит `OrderItem` с нужным товаром;
- статус заказа входит в список подтверждённых статусов.

Статусы, которые не дают право на отзыв:

```text
new
cancelled
```

Дополнительная проверка успешного `Payment` на этапе 11 не вводится. В текущей архитектуре именно статус `Order` является агрегированным бизнес-состоянием заказа, а `Payment` остаётся детализацией платёжной истории.

## Возвраты и будущая refund-логика

На будущее фиксируется принцип: если факт покупки был подтверждён, последующий возврат не должен автоматически удалять право оставить отзыв.

Причина: возврат не всегда означает, что пользователь не имел опыта использования товара. Он может быть связан с качеством, повреждением, несоответствием ожиданиям или другой причиной.

Если позже появятся отдельные сущности `Refund`, `ReturnRequest`, `Chargeback`, `Dispute` или антифрод-логика, изменение этого правила должно оформляться отдельным ADR.

## Правило для `Review.is_verified_purchase`

`Review.is_verified_purchase` выставляется в `True`, если на момент создания отзыва сервис подтвердил наличие покупки через `Order` и `OrderItem`.

Публичный пользовательский сценарий этапа 11 не создаёт отзывы без подтверждённой покупки с `is_verified_purchase=False`.

## Инварианты реализации

1. Отзыв может оставить только авторизованный пользователь.
2. У пользователя должен быть заказ с товаром в статусе `paid`, `processing`, `shipped` или `completed`.
3. Заказы в статусах `new` и `cancelled` не подтверждают право на отзыв.
4. Проверка права на отзыв выполняется в `reviews.services`.
5. `reviews.services` не проверяет `Payment` напрямую на этапе 11.
6. Один пользователь может оставить только один отзыв на один товар.
7. Повторная покупка того же товара не даёт право на второй отзыв.
8. При успешном создании отзыва выставляется `is_verified_purchase=True`.

## Ожидаемый сервисный контракт

```python
from apps.orders.models import Order


REVIEW_ELIGIBLE_ORDER_STATUSES = (
    Order.Status.PAID,
    Order.Status.PROCESSING,
    Order.Status.SHIPPED,
    Order.Status.COMPLETED,
)


def user_can_review_product(user, product) -> bool:
    """
    Проверяет, может ли пользователь оставить отзыв на товар.
    """
    if not user.is_authenticated:
        return False

    return Order.objects.filter(
        user=user,
        status__in=REVIEW_ELIGIBLE_ORDER_STATUSES,
        items__product=product,
    ).exists()
```

## Последствия

Плюсы:

- правило простое и проверяется прямым запросом через `OrderItem`;
- checkout и reviews используют статус `Order` как источник бизнес-состояния;
- не дублируется платёжная логика внутри reviews;
- пользователь может оставить отзыв сразу после оплаченного заказа;
- будущая refund-логика не ломает текущее право на отзыв без отдельного решения.

Минусы:

- пользователь может оставить отзыв до фактического получения товара;
- статус `paid` считается достаточным подтверждением покупки;
- без отдельной refund/anti-fraud логики нельзя различить добросовестный возврат и спорный платёж.
