# ADR 0008: Несколько платежей на один заказ

## Статус

Принято.

## Контекст

В текущей модели приложения `payments.Payment.order` реализован как `ForeignKey` на модель `Order`.

Это означает связь:

```text
Order 1 -> N Payment
```

То есть один заказ может иметь несколько связанных платежей.

Конфликт C004 возник из-за необходимости явно определить бизнес-правило:

- должен ли заказ иметь только один платёж;
- или заказ может иметь несколько платежей.

Для простого MVP достаточно модели Order 1 -> 1 Payment, так как она проще в реализации и требует меньше логики обработки статусов.

Однако для более реалистичной модели интернет-магазина связь Order 1 -> N Payment является более гибкой и лучше подходит для будущего развития проекта.

## Решение

Оставляем текущую модель:

```
Order 1 -> N Payment
```

Модель Payment продолжает ссылаться на Order через ForeignKey.

Один заказ может иметь несколько платежных записей.

На текущем этапе это используется не для сложной финансовой логики, а как задел под следующие сценарии:

- повторная попытка оплаты после ошибки;
- хранение истории попыток оплаты;
- поддержка разных платёжных провайдеров в будущем;
- возможность отдельного учёта успешных, неуспешных и отменённых платежей;
- подготовка к возвратам или частичным операциям в следующих версиях проекта.

При этом для MVP checkout-логика должна быть ограничена простым правилом:
```
У заказа может быть несколько Payment-записей,
но только один актуальный успешный платёж.
```
Рекомендуемое правило для бизнес-логики:

- новые попытки оплаты создают новые записи Payment;
- старые платежи не перезаписываются;
- успешный платёж переводит заказ в оплаченный статус;
- повторная успешная оплата уже оплаченного заказа должна быть запрещена бизнес-логикой;
- неуспешные попытки оплаты остаются в истории.

## Последствия

Плюсы решения:

- сохраняется текущая структура кода без лишней переделки модели;
- появляется история попыток оплаты;
- проще реализовать повторную оплату после ошибки;
- проект становится ближе к реальным e-commerce-системам;
- в будущем можно добавить возвраты, частичные оплаты и несколько провайдеров;
- модель лучше масштабируется по бизнес-логике.

Минусы решения:

- checkout-логика становится сложнее, чем при связи Order 1 -> 1 Payment;
- нужно явно контролировать, что у заказа не возникает несколько успешных платежей;
- потребуется аккуратная работа со статусами Order и Payment;
- тестов потребуется больше, чем для простой модели одного платежа.

```text
3. У одного заказа не должно быть больше одного successful Payment.
4. Нельзя повторно оплатить уже оплаченный заказ.
```
