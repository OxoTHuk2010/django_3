# ADR 0002: Подход к корзине

## Статус

Принято.

## Контекст

В проекте интернет-магазина требуется реализовать корзину покупателя.

Корзина должна поддерживать два сценария:

1. Неавторизованный пользователь добавляет товары в корзину до входа в систему.
2. Авторизованный пользователь работает с постоянной корзиной, привязанной к его аккаунту.

Также необходимо учитывать следующие требования:

- не создавать лишнюю нагрузку на базу данных для гостевых пользователей;
- не доверять данным, пришедшим от клиента;
- не хранить в корзине устаревающие данные вроде цены, названия товара и остатка;
- проверять актуальную цену и наличие товара;
- корректно объединять гостевую корзину с корзиной пользователя после авторизации;
- обеспечить безопасное оформление заказа с повторной проверкой остатков;
- подготовить архитектуру к дальнейшему развитию: скидки, промокоды, заказы, платежи, история покупок.

Основная проблема заключается в том, что корзина не является финансово значимой сущностью сама по себе. Она отражает намерение пользователя купить товар, но не должна считаться источником истины по цене, остаткам или доступности товара.

Источником истины должны оставаться доменные модели каталога и склада, например `Product`.


## Варианты

### Вариант A: Хранить все корзины в БД
Хранить все корзины в БД

Все пользователи, включая гостей, получают запись в БД.

Плюсы:

- единый механизм хранения;
- проще строить аналитику;
- проще переносить корзину между устройствами, если есть идентификатор.

Минусы:

- много мусорных корзин от гостей;
- повышенная нагрузка на БД;
- требуется регулярная очистка старых корзин;
- выше риск злоупотреблений со стороны ботов;
- сложнее отличать реальные пользовательские намерения от случайных действий.

Решение отклонено для гостевых пользователей.

### Вариант B: Хранить всю корзину только в session

Корзина даже для авторизованных пользователей хранится только в session.

Плюсы:

- меньше моделей;
- проще начальная реализация;
- меньше записей в БД.

Минусы:

- корзина не сохраняется между устройствами;
- пользователь может потерять корзину;
- сложнее поддерживать постоянный пользовательский сценарий;
- невозможно удобно анализировать корзины авторизованных пользователей;
- хуже UX для зарегистрированных пользователей.

Решение отклонено для авторизованных пользователей.

### Вариант C: Хранить гостевую корзину полностью на клиенте

Frontend хранит корзину в localStorage или cookie.

Плюсы:

- минимальная нагрузка на backend;
- не требуется server-side session;
- удобно для SPA.

Минусы:

- клиентским данным нельзя доверять;
- данные легко изменить;
- сложнее синхронизация;
- хуже контроль бизнес-логики;
- требуется дополнительная серверная нормализация при каждом запросе.

Решение может быть рассмотрено в будущем для отдельного frontend/API-first сценария, но на текущем этапе отклонено.

### Вариант D: Резервировать товар при добавлении в корзину

При добавлении товара в корзину складской остаток временно резервируется.

Плюсы:

- пользователь видит более гарантированную доступность товара;
- снижается риск ситуации, когда товар исчезает перед checkout.

Минусы:

- резко усложняется бизнес-логика;
- нужны TTL-резервы;
- нужна фоновая очистка истёкших резервов;
- возможна атака на блокировку остатков;
- требуется отдельная модель резервирования;
- преждевременно для текущего этапа проекта.

Решение отклонено на текущем этапе.

Возможное развитие в будущем:

- StockReservation
- reserved_until
- reservation_status
- background cleanup task

## Решение

Принято использовать комбинированный подход:

```text
неавторизованный пользователь -> корзина хранится в session
авторизованный пользователь   -> корзина хранится в базе данных
```

Для неавторизованных пользователей корзина хранится в пользовательской сессии.

Для авторизованных пользователей корзина хранится в БД с использованием моделей:

```
Cart
CartItem
```

После успешной авторизации гостевая корзина из session объединяется с постоянной корзиной пользователя в БД.

## Основные правила
1. В корзине хранится только минимальный набор данных

Для гостевой корзины в session хранятся только:

```
product_id
quantity
```
Пример структуры session-cart:

{
    "cart": {
        "15": {
            "quantity": 2
        },
        "27": {
            "quantity": 1
        }
    }
}

В CartItem для авторизованного пользователя также хранятся только:

```
cart
product
quantity
```

В корзине не хранятся:

```
цена товара
название товара
скидка
остаток
итоговая сумма
снимок данных товара
```

Эти данные могут измениться и поэтому должны подтягиваться из актуального состояния системы.

2. Цена и остаток всегда берутся из актуального Product

При отображении корзины backend должен заново получить товары из базы данных и рассчитать:

```
текущую цену
актуальное наличие
активность товара
итоговую стоимость позиции
итоговую стоимость всей корзины
```

Клиент не имеет права передавать цену товара или итоговую сумму как доверенные данные.

Клиент может передавать только:
```
product_id
quantity
```

3. Корзина не резервирует товар

Добавление товара в корзину не означает резервирование товара на складе.

Причины:
```
пользователь может добавить товар и не оформить заказ;
боты могут массово блокировать складские остатки;
потребуется TTL для резерва;
потребуется отдельная модель резервирования;
усложняется бизнес-логика отмены и очистки резервов.
```

На текущем этапе резервирование товара не реализуется.

Проверка остатков выполняется:

```
при добавлении товара в корзину
при отображении корзины
при оформлении заказа
```

Финальная и обязательная проверка выполняется именно при оформлении заказа.

4. При checkout выполняется строгая транзакционная проверка

Оформление заказа должно выполняться внутри транзакции.

На этапе создания заказа необходимо повторно проверить:

```
товар существует
товар активен
остатка достаточно
количество корректное
цена актуальна
```

Для защиты от гонок при покупке товара необходимо использовать блокировку строк товара:

Product.objects.select_for_update()

Пример принципа:

```python
with transaction.atomic():
    product = Product.objects.select_for_update().get(id=product_id)

    if product.stock_quantity < quantity:
        raise ValidationError("Недостаточно товара на складе")

    product.stock_quantity -= quantity
    product.save(update_fields=["stock_quantity"])
```

5. Snapshot цены сохраняется только в заказе

Корзина не хранит цену.

Цена фиксируется только при создании заказа.

В OrderItem необходимо сохранять snapshot-данные:

```
product
product_name
unit_price
quantity
total_price
```

Это нужно потому, что после оформления заказа цена товара может измениться, но уже созданный заказ не должен изменяться.

Пример:

```python
class OrderItem(models.Model):
    order = models.ForeignKey(
        "orders.Order",
        on_delete=models.CASCADE,
        related_name="items",
    )
    product = models.ForeignKey(
        "catalog.Product",
        on_delete=models.PROTECT,
        related_name="order_items",
    )
    product_name = models.CharField(max_length=255)
    unit_price = models.DecimalField(max_digits=10, decimal_places=2)
    quantity = models.PositiveIntegerField()
    total_price = models.DecimalField(max_digits=10, decimal_places=2)
```

6. После логина гостевая корзина объединяется с DB-корзиной

После успешной авторизации необходимо объединить session-cart с корзиной пользователя в БД.

Принята стратегия:

```
если товар уже есть в DB-корзине, количество складывается
если товара нет в DB-корзине, он добавляется
итоговое количество ограничивается остатком товара и системным лимитом
после успешного merge session-cart очищается
```

Пример логики:

```python
final_quantity = min(
    db_quantity + session_quantity,
    product.stock_quantity,
    MAX_CART_ITEM_QUANTITY,
)
```

Такой подход выбран потому, что он не теряет действия пользователя, выполненные до авторизации.
