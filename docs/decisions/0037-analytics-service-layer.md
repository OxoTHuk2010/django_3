# ADR 0037: Общий service layer для аналитики

## Статус

Принято. Уточнение от 2026-05-24: GraphQL-этап исключён из текущего scope, но общий слой аналитики остаётся действующим решением для admin dashboard и возможного будущего API-слоя.

## Контекст

Аналитика уже требуется в staff-only admin dashboard. Изначально также рассматривался GraphQL endpoint `/graphql/`, но этап 28 исключён из текущего scope.

Источники данных: `Order`, `OrderItem`, `Payment`, `Product`, `Review`, `User`. Если расчёты держать внутри admin views или будущих API/resolver-слоёв, метрики могут разойтись.

## Решение

Строить аналитику через общий read/service слой.

Общий слой отвечает за:

- расчёт выручки;
- количество заказов;
- средний чек;
- новых пользователей;
- оплаченные заказы;
- популярные товары;
- агрегаты, нужные admin dashboard и возможному будущему API-слою.

Admin dashboard не дублирует расчёты. Если GraphQL или другой API-слой вернётся позже, он должен переиспользовать этот слой и отвечать только за доступ, представление и формат ответа.

## Последствия

Плюсы:

- admin и возможный будущий API-слой будут показывать одинаковые метрики;
- основные тесты агрегатов пишутся один раз на service layer;
- будущие изменения формул не нужно синхронизировать в двух местах.

Минусы:

- перед UI/API реализацией нужно выделить явный analytics module;
- слой должен иметь понятные контракты фильтров, периодов и статусов;
- presentation tests всё равно нужны для каждого входного слоя, который использует аналитику.

## Инварианты

- Расчёты метрик не живут внутри templates, admin views или API/resolver-слоёв.
- Staff-only access проверяется на уровне входных endpoint/view/resolver.
- Общий слой покрывается тестами агрегатов.
- Admin и любой будущий API-слой покрываются тестами доступа, формата ответа и smoke-сценариев.
