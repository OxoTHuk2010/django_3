# Конфликты и решения

Этот файл фиксирует текущие архитектурные противоречия и вопросы, которые нельзя прятать внутри README или базовой документации. Решённые конфликты остаются здесь как журнал принятых решений, если они влияли на roadmap.

## C001. Корзина: гибридный подход session + database-backed

Статус: решён.

Связанный ADR: `docs/decisions/0002-session-cart.md`.

### Принятое решение

ADR 0002 принимает комбинированный подход:

- неавторизованный пользователь хранит корзину в Django session;
- авторизованный пользователь хранит корзину в БД через `Cart` и `CartItem`;
- после логина session-cart объединяется с DB-корзиной пользователя;
- корзина хранит только `product_id` и `quantity`, а цена, активность и остатки всегда берутся из актуального `Product`;
- корзина не резервирует товар;
- финальная проверка остатков выполняется при checkout внутри транзакции.

### Что изменилось по конфликту

Предыдущий конфликт между `session cart` и `database-backed cart` закрыт: это больше не взаимоисключающие варианты, а две части одной архитектуры.

### Что остаётся сделать в реализации

- Реализовать session-cart для гостя.
- Реализовать сервис работы с DB-корзиной авторизованного пользователя.
- Реализовать merge session-cart в DB-cart после успешного логина.
- Ограничить итоговое количество при merge по `stock_quantity` и системному лимиту.
- Покрыть правила корзины тестами.

## C002. Soft delete в базовой модели

Статус: в обсуждении.

### Факт по текущему коду

В `common` есть `SoftDeleteModel`. `Category` и `Product` наследуют soft delete.

### Риск

Если soft delete используется частично, публичные queryset могут случайно показывать удалённые товары или категории.

### Вариант A. Оставить soft delete

- Ввести selectors, которые всегда фильтруют `is_deleted=False`.
- Описать правило в `docs/business-rules.md`.
- Покрыть selectors тестами.

### Вариант B. Убрать soft delete на MVP

- Упростить модель и запросы.
- Вернуть soft delete позже, когда появится отдельная потребность.

### Рекомендуемое решение

Оставлять soft delete стоит только вместе с selectors и тестами. Иначе это создаёт скрытый риск для каталога.

## C003. Email как основной логин

Статус: требует проверки через пользовательские сценарии.

### Факт по текущему коду

`users.User` использует email как основной логин и наследует `AbstractUser`.

### Что проверить

- `createsuperuser` внутри Docker.
- Вход в admin.
- JWT token obtain.
- Уникальность email.
- Поведение поля `username`, если email является основным идентификатором.

## C004. Несколько платежей на один заказ или один платёж на заказ

Статус: в обсуждении.

### Факт по текущему коду

`payments.Payment.order` сейчас реализован как `ForeignKey` на `Order`. Это означает связь `Order 1 -> N Payment`.

### Когда нужен один платёж

- простой MVP;
- mock-оплата;
- меньше логики статусов.

### Когда нужно несколько платежей

- повторная попытка оплаты;
- частичная оплата;
- возвраты;
- несколько провайдеров.

### Рекомендуемое решение

Для текущей модели можно оставить `Order 1 -> N Payment`, но это решение нужно явно зафиксировать в документации и будущей логике checkout.

## C005. Связь пользователя и отзыва

Статус: требует исправления до создания миграций.

### Факт по текущему коду

`reviews.Review.user` сейчас реализован как `OneToOneField` на пользователя. При этом в модели также есть `UniqueConstraint(fields=["user", "product"])`.

### Почему это конфликт

Бизнес-правило проекта: один пользователь может оставить только один отзыв на один товар.

Текущая связь `OneToOneField` означает более жёсткое правило: один пользователь может оставить только один отзыв вообще, независимо от товара. Тогда ограничение `user + product` становится избыточным и не выражает реальное правило.

### Рекомендуемое решение

Заменить `Review.user` на `ForeignKey(settings.AUTH_USER_MODEL, related_name="reviews")` и оставить уникальность пары `user + product`. Это соответствует правилу: пользователь может оставить отзывы к разным товарам, но не может оставить второй отзыв на тот же товар.
