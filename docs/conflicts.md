# Конфликты и решения в обсуждении

Этот файл фиксирует текущие архитектурные противоречия и вопросы, которые нельзя прятать внутри README или базовой документации. Когда конфликт решён, соответствующий ADR должен быть обновлён, а код и документация должны быть синхронизированы.

## C001. Корзина: session-based или database-backed

Статус: в обсуждении.

Связанный ADR: `docs/decisions/0002-session-cart.md`.

### Факт по текущему коду

В коде есть `cart.Cart` и `cart.CartItem`, то есть реализована database-backed корзина для авторизованного пользователя.

### Факт по исходному плану

Исходный план и ADR 0002 описывают session-based корзину для web-интерфейса.

### Почему это конфликт

Session cart и database-backed cart — разные архитектурные подходы:

- отличаются хранением данных;
- отличаются правилами для гостя и авторизованного пользователя;
- отличаются тесты;
- отличаются API и web-flow;
- отличаются миграции.

Нельзя одновременно считать session cart принятым решением и мигрировать DB cart как финальную модель без пересмотра ADR.

### Вариант A. Оставить session cart

Плюсы:

- проще для web MVP;
- не нужны таблицы корзины;
- гость может пользоваться корзиной без авторизации;
- соответствует исходному плану.

Минусы:

- сложнее синхронизировать корзину между устройствами;
- для API может понадобиться отдельная логика.

Что сделать:

- убрать DB-модели `Cart` и `CartItem` до создания миграций;
- реализовать `apps/cart/cart.py` и session service на этапе корзины;
- оставить ADR 0002 решением про session cart.

### Вариант B. Принять database-backed cart

Плюсы:

- корзина хранится в БД;
- проще связывать корзину с пользователем;
- проще делать API корзины для авторизованных пользователей;
- данные не теряются при смене устройства.

Минусы:

- нужно решить сценарий гостя;
- появляются таблицы и миграции;
- усложняется MVP;
- ADR 0002 нужно изменить.

Что сделать:

- обновить ADR 0002: статус `Принято`, решение — database-backed cart;
- описать гостевую корзину отдельно;
- добавить constraints и тесты для `Cart`/`CartItem`.

### Рекомендуемое решение

Для первоначального web MVP лучше оставить session cart. Database-backed cart имеет смысл принимать только если цель этапа расширяется до API-корзины или синхронизации корзины между устройствами.

## C002. Soft delete в базовой модели

Статус: в обсуждении.

### Факт по текущему коду

В `common` есть `SoftDeleteModel`. `Category` и `Product` наследуют soft delete.

### Риск

Если soft delete используется частично, публичные queryset могут случайно показывать удалённые товары или категории.

### Вариант A. Оставить soft delete

- Ввести selectors, которые всегда фильтруют `is_deleted=False`.
- Описать правило в `docs/business-rules.md`.
- Покрыть selectors тестами.

### Вариант B. Убрать soft delete на MVP

- Упростить модель и запросы.
- Вернуть soft delete позже, когда появится отдельная потребность.

### Рекомендуемое решение

Оставлять soft delete стоит только вместе с selectors и тестами. Иначе это создаёт скрытый риск для каталога.

## C003. Email как основной логин

Статус: требует проверки через пользовательские сценарии.

### Факт по текущему коду

`users.User` использует email как основной логин и наследует `AbstractUser`.

### Что проверить

- `createsuperuser` внутри Docker.
- Вход в admin.
- JWT token obtain.
- Уникальность email.
- Поведение поля `username`, если email является основным идентификатором.

## C004. Несколько платежей на один заказ или один платёж на заказ

Статус: в обсуждении.

### Факт по текущему коду

`payments.Payment.order` сейчас реализован как `ForeignKey` на `Order`. Это означает связь `Order 1 -> N Payment`.

### Когда нужен один платёж

- простой MVP;
- mock-оплата;
- меньше логики статусов.

### Когда нужно несколько платежей

- повторная попытка оплаты;
- частичная оплата;
- возвраты;
- несколько провайдеров.

### Рекомендуемое решение

Для текущей модели можно оставить `Order 1 -> N Payment`, но это решение нужно явно зафиксировать в документации и будущей логике checkout.

## C005. Связь пользователя и отзыва

Статус: требует исправления до создания миграций.

### Факт по текущему коду

`reviews.Review.user` сейчас реализован как `OneToOneField` на пользователя. При этом в модели также есть `UniqueConstraint(fields=["user", "product"])`.

### Почему это конфликт

Бизнес-правило проекта: один пользователь может оставить только один отзыв на один товар.

Текущая связь `OneToOneField` означает более жёсткое правило: один пользователь может оставить только один отзыв вообще, независимо от товара. Тогда ограничение `user + product` становится избыточным и не выражает реальное правило.

### Рекомендуемое решение

Заменить `Review.user` на `ForeignKey(settings.AUTH_USER_MODEL, related_name="reviews")` и оставить уникальность пары `user + product`. Это соответствует правилу: пользователь может оставить отзывы к разным товарам, но не может оставить второй отзыв на тот же товар.
