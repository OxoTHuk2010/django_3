# Конфликты и решения

Этот файл фиксирует текущие архитектурные противоречия и вопросы, которые нельзя прятать внутри README или базовой документации. Решённые конфликты остаются здесь как журнал принятых решений, если они влияли на roadmap.

## C001. Корзина: гибридный подход session + database-backed

Статус: решён.

Связанный ADR: `docs/decisions/0002-session-cart.md`.

### Принятое решение

ADR 0002 принимает комбинированный подход:

- неавторизованный пользователь хранит корзину в Django session;
- авторизованный пользователь хранит корзину в БД через `Cart` и `CartItem`;
- после логина session-cart объединяется с DB-корзиной пользователя;
- корзина хранит только `product_id` и `quantity`, а цена, активность и остатки всегда берутся из актуального `Product`;
- корзина не резервирует товар;
- финальная проверка остатков выполняется при checkout внутри транзакции.

### Что изменилось по конфликту

Предыдущий конфликт между `session cart` и `database-backed cart` закрыт: это больше не взаимоисключающие варианты, а две части одной архитектуры.

### Что остаётся сделать в реализации

- Реализовать session-cart для гостя.
- Реализовать сервис работы с DB-корзиной авторизованного пользователя.
- Реализовать merge session-cart в DB-cart после успешного логина.
- Ограничить итоговое количество при merge по `stock_quantity` и системному лимиту.
- Покрыть правила корзины тестами.

## C002. Soft delete в базовой модели

Статус: решён.

Связанный ADR: `docs/decisions/0006-soft-delete.md`.

### Факт по текущему коду

В `common` есть отдельный `SoftDeleteModel`. `TimeStampedModel` не содержит `is_deleted` и `deleted_at`.

По текущему коду `SoftDeleteModel` используется только в `catalog`:

- `catalog.Category`;
- `catalog.Product`.

### Принятое решение

ADR 0006 принимает ограниченное использование soft delete:

- не добавлять soft delete в универсальный `TimeStampedModel`;
- держать soft delete отдельным mixin/abstract-классом;
- использовать `SoftDeleteModel` только для `Product` и `Category`;
- не подключать soft delete к заказам, оплатам, позициям заказа и другим исторически значимым сущностям;
- пересматривать ADR 0006, если soft delete понадобится другим моделям.

### Что остаётся сделать в реализации

- В selectors каталога всегда исключать `is_deleted=True`.
- Покрыть публичные выборки каталога тестами.

## C003. Основной логин пользователя

Статус: решён.

Связанный ADR: `docs/decisions/0007-username-user-login.md`.

### Факт по текущему коду

`users.User` наследует `AbstractUser` и использует стандартный логин Django:

```text
USERNAME_FIELD = "username"
REQUIRED_FIELDS = []
```

Поле `email` является вспомогательным контактным полем:

```text
blank=True
null=True
unique=True
```

### Принятое решение

ADR 0007 фиксирует:

- основной логин пользователя — `username`;
- `email` не участвует в основной аутентификации;
- стандартные сценарии Django Admin, `createsuperuser` и JWT token obtain используют `username`;
- переход к login by email возможен только через отдельный ADR и изменение логики аутентификации.

Конфликт закрыт. Текущая модель и миграции соответствуют ADR 0007.

## C004. Несколько платежей на один заказ или один платёж на заказ

Статус: решён.

Связанный ADR: `docs/decisions/0008-payment-order.md`.

### Факт по текущему коду

`payments.Payment.order` сейчас реализован как `ForeignKey` на `Order`. Это означает связь `Order 1 -> N Payment`.

### Принятое решение

ADR 0008 фиксирует:

- один заказ может иметь несколько `Payment`-записей;
- новые попытки оплаты создают новые записи, старые платежи не перезаписываются;
- неуспешные, отменённые и возвращённые платежи остаются в истории;
- для MVP checkout должен ограничивать успешную оплату правилом: у заказа не должно быть больше одного актуального успешного платежа;
- повторная успешная оплата уже оплаченного заказа должна быть запрещена бизнес-логикой.

### Что остаётся сделать в реализации

- Реализовать правило запрета повторной успешной оплаты в checkout/payment service.
- Покрыть сценарии оплаты тестами.

## C005. Связь пользователя и отзыва

Статус: решён.

### Факт по текущему коду

`reviews.Review.user` реализован как `ForeignKey` на пользователя.

В модели также есть `UniqueConstraint(fields=["user", "product"])`.

### Принятое решение

Текущая модель соответствует бизнес-правилу:

- пользователь может оставить отзывы к разным товарам;
- пользователь не может оставить второй отзыв на тот же товар.

Конфликт закрыт. Текущая модель и миграции соответствуют бизнес-правилу отзывов.

## C006. URL детальной страницы товара

Статус: решён.

Связанный этап: этап 7 — страница товара.

### Факт по текущей документации

В `docs/roadmap.md` для этапа 7 зафиксирован маршрут:

```text
/products/<slug>/
```

Маршрут списка товаров уже использует тот же namespace:

```text
/products/
```

### Принятое решение

Канонический web URL детальной страницы товара:

```text
/products/<slug>/
```

Причина: детальная страница остаётся внутри общего namespace каталога `/products/`, а публичные ссылки списка и карточки товара выглядят последовательно.

### Что остаётся сделать в реализации

- Добавить URL `/products/<slug>/` в `catalog.urls`.
- Реализовать `ProductDetailView`.
- Добавить selector получения одного публичного товара по `slug`.
- Покрыть доступность активного товара и недоступность неактивного/soft-deleted товара тестами.

## C007. Источник изображения на детальной странице товара

Статус: решён.

Связанный этап: этап 7 — страница товара.

Связанный ADR: `docs/decisions/0009-img-source.md`.

### Факт по текущему коду

В модели каталога уже есть `ProductImage` с полями:

- `product`;
- `image`;
- `alt_text`;
- `is_main`;
- `sort_order`;
- `created_at`;
- `updated_at`.

В `src/prepare/` есть подготовленные UI-ассеты и изображения, но эта директория не должна становиться runtime-зависимостью рабочей реализации этапа 7.

### Принятое решение

ADR 0009 фиксирует:

- источником изображения товара на детальной странице является только `ProductImage`;
- обязательный fallback-placeholder на этапе 7 не добавляется;
- если у товара нет связанных `ProductImage`, страница должна корректно отображаться без изображения;
- допустимо не показывать блок изображения или показать текстовое состояние `Изображение отсутствует`;
- запрещено подбирать изображение по `slug`;
- запрещено напрямую использовать файлы из `src/prepare/` в рабочем шаблоне;
- запрещено зашивать пути к изображениям во view или template вне модели `ProductImage`;
- основное изображение определяется через `ProductImage.is_main`.

### Что изменилось по конфликту

Предыдущий конфликт между `ProductImage`, placeholder и прямым использованием `src/prepare/` закрыт.

На этапе 7 не нужно добавлять placeholder и не нужно переносить изображения из `src/prepare/` в runtime-статику. Отсутствие изображения является допустимым состоянием интерфейса.

### Что остаётся сделать в реализации

- В selector/view детальной страницы получать изображения через связь `ProductImage`.
- В шаблоне корректно обработать товар без изображений.
- Не использовать `src/prepare/` напрямую.
- Добавить тесты для товара с изображением и без изображения.

## C008. Кнопка покупки на странице товара до реализации корзины

Статус: решён.

Связанный этап: этап 7 — страница товара.

Связанный ADR: `docs/decisions/0010-button.md`.

### Факт по текущему roadmap

Этап 7 реализует детальную страницу товара, но корзина реализуется только на этапе 8.

Поэтому на этапе 7 нельзя добавлять активную POST-форму покупки без backend-логики корзины.

### Принятое решение

ADR 0010 фиксирует:

- для товара с `stock_quantity > 0` показывать disabled-кнопку `Добавить в корзину`;
- рядом или под кнопкой показывать пояснение, что корзина будет доступна позже;
- для товара с `stock_quantity = 0` показывать состояние `Нет в наличии`;
- не выполнять POST-запросы на добавление товара в корзину;
- не создавать временную frontend-корзину;
- активную форму добавления товара в корзину реализовывать только на этапе 8.

### Что изменилось по конфликту

Предыдущий конфликт между скрытой кнопкой, disabled-кнопкой и временной frontend-симуляцией закрыт.

На этапе 7 показываем будущую точку действия, но не реализуем покупку.

### Что остаётся сделать в реализации

- Добавить disabled-кнопку в шаблон детальной страницы.
- Добавить пояснение рядом с кнопкой.
- Для `stock_quantity = 0` показать `Нет в наличии`.
- Покрыть disabled-состояние тестами.
- Проверить, что на этапе 7 нет активной POST-формы добавления в корзину.


## C009. Отзывы и рейтинг на странице товара до реализации review service

Статус: решён.

Связанный этап: этап 7 — страница товара.

Связанный ADR: `docs/decisions/0011-reviews-rating.md`.

### Факт по текущему коду

Модель `Review` уже есть и содержит поле `status`.

Публичный статус отзыва:

```text
Review.Status.PUBLISHED
```

Полноценный review service, форма создания отзыва и проверка покупки относятся к более позднему этапу.

### Принятое решение

ADR 0011 фиксирует:

- на этапе 7 показывать только read-only опубликованные отзывы;
- средний рейтинг считать только по опубликованным отзывам;
- количество отзывов считать только по опубликованным отзывам;
- форму создания отзыва на этапе 7 не добавлять;
- не показывать отзывы в статусах `draft`, `pending`, `rejected`, `hidden` и любых будущих непубличных статусах;
- состояние без отзывов должно отображаться корректно.

### Что изменилось по конфликту

Предыдущий конфликт между read-only отзывами, полным скрытием отзывов и преждевременной формой создания закрыт.

На этапе 7 отзывы используются только на чтение.

### Что остаётся сделать в реализации

- В selector/view детальной страницы получить отзывы по `status=Review.Status.PUBLISHED`.
- Посчитать средний рейтинг по опубликованным отзывам.
- Посчитать количество опубликованных отзывов.
- Добавить read-only блок отзывов в шаблон.
- Не добавлять форму создания отзыва.
- Покрыть публичные и непубличные отзывы тестами.


## C010. Правило похожих товаров на странице товара

Статус: решён.

Связанный этап: этап 7 — страница товара.

Связанный ADR: `docs/decisions/0012-rule-product.md`.

### Факт по текущему коду

В текущей модели каталога нет тегов, брендов, атрибутов, просмотров и полноценной рекомендательной системы.

Для минимальной выборки уже доступны:

- `Product.category`;
- `Product.is_active`;
- `Product.is_deleted`;
- `Product.stock_quantity`;
- `Category.is_active`.

### Принятое решение

ADR 0012 фиксирует:

- похожие товары выбираются только из той же категории;
- текущий товар исключается;
- в блок попадают только активные неудалённые товары;
- категория похожих товаров должна быть активной;
- максимум отображается 3 товара;
- товары с `stock_quantity = 0` можно показывать, но с состоянием `Нет в наличии`;
- подбор по цене, тегам, брендам, популярности, заказам и просмотрам на этапе 7 не реализуется.

### Что изменилось по конфликту

Предыдущий конфликт между простой категорией, близкой ценой и рекомендательной логикой закрыт.

На этапе 7 используется минимальное правило похожих товаров по категории.

### Что остаётся сделать в реализации

- Добавить selector похожих товаров.
- Исключить текущий товар из результата.
- Ограничить результат 3 товарами.
- Отфильтровать неактивные и soft-deleted товары.
- Проверять активность категории.
- Покрыть правило похожих товаров тестами.

## C011. Web-маршруты и HTTP-контракт корзины

Статус: требует решения.

Связанный этап: этап 8 — корзина.

Связанный ADR: `docs/decisions/0002-session-cart.md`.

### Контекст

ADR 0002 фиксирует, где хранится корзина, но не определяет web-маршруты и HTTP-контракт действий корзины.

На этапе 7 детальная страница товара уже показывает disabled-кнопку `Добавить в корзину`. На этапе 8 эту точку действия нужно заменить на реальную форму.

Перед реализацией нужно выбрать:

- URL страницы корзины;
- URL добавления товара;
- URL изменения количества;
- URL удаления позиции;
- URL очистки корзины;
- допустимые HTTP-методы;
- идентификатор товара в URL или форме.

### Варианты

Вариант A: REST-like web URL с `product_id`

- `GET /cart/` — показать корзину;
- `POST /cart/add/<int:product_id>/` — добавить товар;
- `POST /cart/update/<int:product_id>/` — изменить количество;
- `POST /cart/remove/<int:product_id>/` — удалить товар;
- `POST /cart/clear/` — очистить корзину.

Плюсы:

- простой контракт для Django forms;
- не зависит от `slug`;
- не смешивает web-корзину с будущим API;
- POST-действия явно меняют состояние.

Минусы:

- URL менее человекочитаемый, чем `slug`.

Вариант B: web URL с `slug`

- `POST /cart/add/<slug:slug>/`;
- `POST /cart/update/<slug:slug>/`;
- `POST /cart/remove/<slug:slug>/`.

Плюсы:

- URL выглядит человекочитаемо;
- согласуется с детальной страницей товара.

Минусы:

- корзина хранит `product_id`, поэтому в сервисе всё равно нужен поиск товара;
- изменение `slug` может усложнить старые формы или ссылки.

Вариант C: один endpoint `/cart/` с action-параметром

- `GET /cart/`;
- `POST /cart/` с `action=add|update|remove|clear`.

Плюсы:

- меньше URL.

Минусы:

- хуже читаемость;
- сложнее тестировать отдельные сценарии;
- view легко превращается в большой обработчик с ветвлениями.

### Что нужно решить

- Используем ли отдельные URL для действий корзины.
- Передаём товар через `product_id` или `slug`.
- Разрешаем ли изменение состояния только через POST.
- Делаем ли redirect после успешного POST.

### Рекомендуемое решение

Рекомендация: принять вариант A.

Для web-интерфейса использовать отдельные POST-маршруты с `product_id`, а после успешного действия выполнять redirect на корзину или предыдущую страницу. Это проще тестировать и не смешивает web-контракт с будущим REST API.

## C012. Сервисный слой корзины и граница ответственности view

Статус: требует решения.

Связанный этап: этап 8 — корзина.

Связанный ADR: `docs/decisions/0002-session-cart.md`.

### Контекст

ADR 0002 фиксирует гибридное хранение:

- гость — session;
- авторизованный пользователь — DB `Cart`/`CartItem`.

Но для реализации нужно определить, где будет находиться логика:

- добавления товара;
- удаления товара;
- изменения количества;
- расчёта итогов;
- нормализации недоступных товаров;
- выбора session-cart или DB-cart.

Если поместить эту логику во views, этап 8 нарушит архитектурный принцип проекта: бизнес-логика не должна размазываться по HTTP-слою.

### Варианты

Вариант A: вся логика во views

Плюсы:

- быстрее начать.

Минусы:

- view быстро станет большой;
- сложнее тестировать бизнес-правила;
- session и DB-логика начнут дублироваться.

Вариант B: единый `cart/services.py` как публичный сервисный слой

Плюсы:

- view остаются тонкими;
- правила корзины тестируются отдельно;
- session и DB-логика имеют единый внешний контракт;
- проще использовать те же правила на checkout и API-этапе.

Минусы:

- нужно заранее определить сервисные функции и структуру результата.

Вариант C: отдельные классы `SessionCart` и `DbCart`, а view выбирает нужный класс

Плюсы:

- явное разделение storage-механизмов.

Минусы:

- view знает слишком много о способе хранения;
- выше риск расхождения правил между двумя реализациями.

### Что нужно решить

- Должен ли быть единый публичный service-layer корзины.
- Какие функции считаются минимальным контрактом этапа 8.
- Возвращают ли сервисы готовый snapshot для шаблона или только изменяют storage.

### Рекомендуемое решение

Рекомендация: принять вариант B.

Создать `apps/cart/services.py` с единым публичным контрактом:

- `get_cart_snapshot(request)`;
- `add_to_cart(request, product, quantity)`;
- `update_cart_item(request, product, quantity)`;
- `remove_from_cart(request, product)`;
- `clear_cart(request)`;
- `merge_session_cart_to_user_cart(request, user)`.

View должны только валидировать форму на уровне HTTP, вызывать сервис и показывать результат.

## C013. Когда выполнять merge session-cart в DB-cart

Статус: требует решения.

Связанный этап: этап 8 — корзина.

Связанный ADR: `docs/decisions/0002-session-cart.md`.

### Контекст

ADR 0002 фиксирует, что после успешной авторизации гостевая session-cart объединяется с DB-корзиной пользователя.

Но полноценные web-сценарии регистрации и входа относятся к будущему этапу пользователей. На этапе 8 корзина уже должна иметь merge-логику, но в проекте ещё нет целевой login-view для покупателя.

### Варианты

Вариант A: подключить merge через сигнал `user_logged_in` уже на этапе 8

Плюсы:

- merge сработает при любом успешном Django login;
- логика не зависит от будущей custom login-view.

Минусы:

- может затронуть admin-login;
- сложнее тестировать пользовательский web-flow без готового аккаунтного этапа;
- сигнал скрывает бизнес-действие.

Вариант B: реализовать merge-сервис сейчас, а подключить его к пользовательскому login-flow на этапе аккаунта

Плюсы:

- бизнес-логика будет готова и покрыта тестами;
- нет скрытого поведения через signals;
- не смешивает этап 8 с этапом 10.

Минусы:

- фактический автоматический merge после login появится позже.

Вариант C: не реализовывать merge до этапа пользователей

Плюсы:

- этап 8 проще.

Минусы:

- ADR 0002 и roadmap этапа 8 будут закрыты не полностью;
- позже придётся возвращаться к service-layer корзины.

### Что нужно решить

- Реализуем ли merge-сервис на этапе 8.
- Подключаем ли его сразу к `user_logged_in`.
- Считаем ли отсутствие пользовательского login-flow блокером для полного merge.

### Рекомендуемое решение

Рекомендация: принять вариант B.

На этапе 8 реализовать и протестировать `merge_session_cart_to_user_cart()`, но не подключать его к сигналу. Подключение к реальному login-flow сделать на этапе пользователей, когда появится web-вход.

## C014. Политика количества товара: add, update и merge

Статус: требует решения.

Связанный этап: этап 8 — корзина.

Связанный ADR: `docs/decisions/0002-session-cart.md`.

### Контекст

Для корзины уже есть общие правила:

- quantity должно быть больше нуля;
- quantity не должно превышать остаток;
- при merge итоговое количество ограничивается остатком и системным лимитом.

Но нужно уточнить поведение конкретных операций:

- `add` складывает количество или заменяет;
- `update` заменяет количество или тоже складывает;
- превышение остатка приводит к ошибке или обрезается до доступного остатка;
- нужен ли системный максимум позиции.

### Варианты

Вариант A: `add` складывает, `update` заменяет, пользовательские ошибки не обрезаются silently

Плюсы:

- ожидаемое поведение для интернет-магазина;
- пользователь явно узнаёт о превышении остатка;
- `update` удобно использовать на странице корзины;
- merge может иметь отдельное правило безопасного ограничения.

Минусы:

- нужно аккуратно возвращать сообщения об ошибках.

Вариант B: все операции заменяют количество

Плюсы:

- проще реализация.

Минусы:

- повторное нажатие `Добавить в корзину` не увеличивает количество;
- хуже UX.

Вариант C: все превышения автоматически обрезаются до остатка

Плюсы:

- меньше ошибок для пользователя.

Минусы:

- пользователь может не понять, почему добавилось меньше;
- скрывает бизнес-ошибку.

### Что нужно решить

- `add` складывает или заменяет количество.
- `update` складывает или заменяет количество.
- Пользовательское превышение остатка — ошибка или автоматическое ограничение.
- Какой системный максимум позиции использовать.

### Рекомендуемое решение

Рекомендация: принять вариант A.

Для пользовательских действий:

- `add` увеличивает количество уже существующей позиции;
- `update` заменяет количество;
- если итоговое количество меньше 1 или больше остатка, сервис возвращает ошибку и не меняет корзину;
- системный максимум позиции задать явно, например `MAX_CART_ITEM_QUANTITY = 99`.

Для merge после login можно использовать ограничение `min(db_quantity + session_quantity, stock_quantity, MAX_CART_ITEM_QUANTITY)`, как зафиксировано в ADR 0002.

## C015. Недоступные товары и битые product_id в session-cart

Статус: требует решения.

Связанный этап: этап 8 — корзина.

Связанный ADR: `docs/decisions/0002-session-cart.md`.

### Контекст

Session-cart хранит только `product_id` и `quantity`. За время жизни session товар может быть:

- удалён из БД;
- отключён;
- soft-deleted;
- переведён в скрытую категорию;
- распродан;
- изменён по цене.

ADR 0002 требует брать цену, активность и остаток из актуального `Product`, но не определяет UX и нормализацию для уже лежащих в корзине невалидных позиций.

### Варианты

Вариант A: автоматически удалять недоступные и битые позиции при чтении корзины

Плюсы:

- корзина остаётся чистой;
- checkout не увидит невалидные позиции;
- проще итоговый расчёт.

Минусы:

- пользователь может не понять, куда исчез товар.

Вариант B: показывать недоступные позиции в корзине с предупреждением

Плюсы:

- пользователь видит причину проблемы.

Минусы:

- сложнее snapshot корзины;
- нужно хранить или восстанавливать данные недоступного товара;
- нельзя корректно показать удалённый товар, если его уже нет в БД.

Вариант C: падать с ошибкой при невалидной позиции

Плюсы:

- быстро обнаруживает проблему в разработке.

Минусы:

- плохой UX;
- корзина может стать неоткрываемой.

### Что нужно решить

- Удалять ли невалидные позиции автоматически.
- Нужно ли возвращать пользователю предупреждение о нормализации корзины.
- Как обрабатывать товар без остатка: удалять или показывать как недоступный.

### Рекомендуемое решение

Рекомендация: принять комбинированное решение:

- удалённые, soft-deleted, неактивные товары и товары из скрытых категорий удалять из корзины при нормализации;
- товары с `stock_quantity = 0` оставлять в корзине, но помечать как недоступные для оформления и не позволять checkout;
- если quantity превышает текущий остаток, на этапе просмотра можно показать предупреждение, а изменение количества требовать от пользователя явно;
- сервис должен возвращать список предупреждений для шаблона.

Так корзина не ломается, но пользователь получает объяснимое состояние.
