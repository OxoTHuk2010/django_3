# Конфликты и решения в обсуждении

Этот файл фиксирует текущие архитектурные противоречия и вопросы, которые нельзя прятать внутри README или базовой документации. Когда конфликт решён, соответствующий ADR должен быть обновлён.

## C001. Корзина: session-based или database-backed

Статус: в обсуждении.

Связанный ADR: `docs/decisions/0002-session-cart.md`.

### Контекст

Исходное решение описывало session-based корзину для web-интерфейса. Это соответствует первоначальному плану: корзина живёт в session, а заказ создаётся из корзины на checkout.

В текущей модели появились `cart.Cart` и `cart.CartItem`, то есть database-backed корзина.

### Почему это конфликт

Session cart и database-backed cart — разные архитектурные подходы:

- отличаются хранением данных;
- отличаются правилами для гостя и авторизованного пользователя;
- отличаются тесты;
- отличаются API и web-flow;
- отличаются миграции.

Нельзя одновременно считать ADR про session cart принятым и мигрировать DB cart как финальную модель без пересмотра решения.

### Вариант A. Оставить session cart

Плюсы:

- проще для web MVP;
- не нужны таблицы корзины;
- гость может пользоваться корзиной без авторизации;
- соответствует исходному плану.

Минусы:

- сложнее синхронизировать корзину между устройствами;
- для API может понадобиться отдельная логика.

Что сделать:

- не мигрировать `Cart` и `CartItem` как финальную модель;
- реализовать `apps/cart/cart.py` и session service на этапе корзины;
- оставить ADR 0002 как принятое решение.

### Вариант B. Принять database-backed cart

Плюсы:

- корзина хранится в БД;
- проще связывать корзину с пользователем;
- проще делать API корзины для авторизованных пользователей;
- данные не теряются при смене устройства.

Минусы:

- нужно решить сценарий гостя;
- появляются таблицы и миграции;
- усложняется MVP;
- ADR 0002 нужно изменить.

Что сделать:

- обновить ADR 0002: статус `Принято`, решение — database-backed cart;
- описать гостевую корзину отдельно;
- добавить constraints и тесты для `Cart`/`CartItem`.

### Рекомендуемое решение

Для учебного проекта и первоначального плана лучше оставить session cart для web MVP. Database-backed cart можно добавить позже для API или авторизованных пользователей, если это станет осознанным расширением.

## C002. Soft delete в базовой модели

Статус: в обсуждении.

### Контекст

В `common` добавлен `SoftDeleteModel`. Это полезно для сохранения истории, но требует дисциплины в selectors и публичных queryset.

### Риск

Если soft delete используется частично, можно случайно показывать удалённые товары или категории пользователю.

### Варианты

Вариант A: оставить soft delete.

- Нужно ввести selectors, которые всегда фильтруют `is_deleted=False`.
- Нужно описать правила в тестах.

Вариант B: убрать soft delete на MVP.

- Проще модель и запросы.
- Меньше риска случайно показать удалённые записи.

### Рекомендуемое решение

Если проект ещё на этапе моделей, soft delete можно оставить только при готовности сразу внедрить selectors и тесты. Иначе лучше отложить.

## C003. Email как основной логин

Статус: требует проверки.

### Контекст

`users.User` использует `USERNAME_FIELD = "email"`, но модель всё ещё наследует `AbstractUser`, где есть `username`.

### Риск

Могут потребоваться дополнительные формы для admin и корректная настройка `createsuperuser`.

### Что проверить

- `createsuperuser`.
- Вход в admin.
- JWT token obtain.
- Уникальность email.

## C004. Несколько платежей на один заказ или один платёж на заказ

Статус: в обсуждении.

### Контекст

В целевой схеме можно выбрать:

- `Order 1 -> 1 Payment`;
- `Order 1 -> N Payment`.

### Когда нужен один платёж

- простой MVP;
- mock-оплата;
- меньше логики статусов.

### Когда нужно несколько платежей

- повторная попытка оплаты;
- частичная оплата;
- возвраты;
- несколько провайдеров.

### Рекомендуемое решение

Для MVP можно начать с `Order 1 -> N Payment`, если модель уже проектируется с повторными попытками оплаты. Если цель — минимальная простота, использовать `OneToOneField`.
