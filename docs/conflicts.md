# Конфликты и решения

Этот файл фиксирует текущие архитектурные противоречия и вопросы, которые нельзя прятать внутри README или базовой документации. Решённые конфликты остаются здесь как журнал принятых решений, если они влияли на roadmap.

## C001. Корзина: гибридный подход session + database-backed

Статус: решён.

Связанный ADR: `docs/decisions/0002-session-cart.md`.

### Принятое решение

ADR 0002 принимает комбинированный подход:

- неавторизованный пользователь хранит корзину в Django session;
- авторизованный пользователь хранит корзину в БД через `Cart` и `CartItem`;
- после логина session-cart объединяется с DB-корзиной пользователя;
- корзина хранит только `product_id` и `quantity`, а цена, активность и остатки всегда берутся из актуального `Product`;
- корзина не резервирует товар;
- финальная проверка остатков выполняется при checkout внутри транзакции.

### Что изменилось по конфликту

Предыдущий конфликт между `session cart` и `database-backed cart` закрыт: это больше не взаимоисключающие варианты, а две части одной архитектуры.

### Что остаётся сделать в реализации

- Реализовать session-cart для гостя.
- Реализовать сервис работы с DB-корзиной авторизованного пользователя.
- Реализовать merge session-cart в DB-cart после успешного логина.
- Ограничить итоговое количество при merge по `stock_quantity` и системному лимиту.
- Покрыть правила корзины тестами.

## C002. Soft delete в базовой модели

Статус: решён.

Связанный ADR: `docs/decisions/0006-soft-delete.md`.

### Факт по текущему коду

В `common` есть отдельный `SoftDeleteModel`. `TimeStampedModel` не содержит `is_deleted` и `deleted_at`.

По текущему коду `SoftDeleteModel` используется только в `catalog`:

- `catalog.Category`;
- `catalog.Product`.

### Принятое решение

ADR 0006 принимает ограниченное использование soft delete:

- не добавлять soft delete в универсальный `TimeStampedModel`;
- держать soft delete отдельным mixin/abstract-классом;
- использовать `SoftDeleteModel` только для `Product` и `Category`;
- не подключать soft delete к заказам, оплатам, позициям заказа и другим исторически значимым сущностям;
- пересматривать ADR 0006, если soft delete понадобится другим моделям.

### Что остаётся сделать в реализации

- В selectors каталога всегда исключать `is_deleted=True`.
- Покрыть публичные выборки каталога тестами.

## C003. Основной логин пользователя

Статус: решён.

Связанный ADR: `docs/decisions/0007-username-user-login.md`.

### Факт по текущему коду

`users.User` наследует `AbstractUser` и использует стандартный логин Django:

```text
USERNAME_FIELD = "username"
REQUIRED_FIELDS = []
```

Поле `email` является вспомогательным контактным полем:

```text
blank=True
null=True
unique=True
```

### Принятое решение

ADR 0007 фиксирует:

- основной логин пользователя — `username`;
- `email` не участвует в основной аутентификации;
- стандартные сценарии Django Admin, `createsuperuser` и JWT token obtain используют `username`;
- переход к login by email возможен только через отдельный ADR и изменение логики аутентификации.

Конфликт закрыт. Текущая модель и миграции соответствуют ADR 0007.

## C004. Несколько платежей на один заказ или один платёж на заказ

Статус: решён.

Связанный ADR: `docs/decisions/0008-payment-order.md`.

### Факт по текущему коду

`payments.Payment.order` сейчас реализован как `ForeignKey` на `Order`. Это означает связь `Order 1 -> N Payment`.

### Принятое решение

ADR 0008 фиксирует:

- один заказ может иметь несколько `Payment`-записей;
- новые попытки оплаты создают новые записи, старые платежи не перезаписываются;
- неуспешные, отменённые и возвращённые платежи остаются в истории;
- для MVP checkout должен ограничивать успешную оплату правилом: у заказа не должно быть больше одного актуального успешного платежа;
- повторная успешная оплата уже оплаченного заказа должна быть запрещена бизнес-логикой.

### Что остаётся сделать в реализации

- Реализовать правило запрета повторной успешной оплаты в checkout/payment service.
- Покрыть сценарии оплаты тестами.

## C005. Связь пользователя и отзыва

Статус: решён.

### Факт по текущему коду

`reviews.Review.user` реализован как `ForeignKey` на пользователя.

В модели также есть `UniqueConstraint(fields=["user", "product"])`.

### Принятое решение

Текущая модель соответствует бизнес-правилу:

- пользователь может оставить отзывы к разным товарам;
- пользователь не может оставить второй отзыв на тот же товар.

Конфликт закрыт. Текущая модель и миграции соответствуют бизнес-правилу отзывов.

## C006. URL детальной страницы товара

Статус: решён.

Связанный этап: этап 7 — страница товара.

### Факт по текущей документации

В `docs/roadmap.md` для этапа 7 зафиксирован маршрут:

```text
/products/<slug>/
```

Маршрут списка товаров уже использует тот же namespace:

```text

```

### Принятое решение

Канонический web URL детальной страницы товара:

```text

```

Причина: детальная страница остаётся внутри общего namespace каталога `/products/`, а публичные ссылки списка и карточки товара выглядят последовательно.

- Добавить URL `/products/<slug>/` в `catalog.urls`.
- Реализовать `ProductDetailView`.
- Добавить selector получения одного публичного товара по `slug`.
- Покрыть доступность активного товара и недоступность неактивного/soft-deleted товара тестами.

## C007. Источник изображения на детальной странице товара

Статус: решён.

Связанный этап: этап 7 — страница товара.

Связанный ADR: `docs/decisions/0009-img-source.md`.

### Факт по текущему коду

В модели каталога уже есть `ProductImage` с полями:

- `product`;
- `image`;
- `alt_text`;
- `is_main`;
- `sort_order`;
- `created_at`;
- `updated_at`.

В `src/prepare/` есть подготовленные UI-ассеты и изображения, но эта директория не должна становиться runtime-зависимостью рабочей реализации этапа 7.

### Принятое решение

ADR 0009 фиксирует:

- источником изображения товара на детальной странице является только `ProductImage`;
- обязательный fallback-placeholder на этапе 7 не добавляется;
- если у товара нет связанных `ProductImage`, страница должна корректно отображаться без изображения;
- допустимо не показывать блок изображения или показать текстовое состояние `Изображение отсутствует`;
- запрещено подбирать изображение по `slug`;
- запрещено напрямую использовать файлы из `src/prepare/` в рабочем шаблоне;
- запрещено зашивать пути к изображениям во view или template вне модели `ProductImage`;
- основное изображение определяется через `ProductImage.is_main`.

### Что изменилось по конфликту

Предыдущий конфликт между `ProductImage`, placeholder и прямым использованием `src/prepare/` закрыт.

На этапе 7 не нужно добавлять placeholder и не нужно переносить изображения из `src/prepare/` в runtime-статику. Отсутствие изображения является допустимым состоянием интерфейса.

### Что остаётся сделать в реализации

- В selector/view детальной страницы получать изображения через связь `ProductImage`.
- В шаблоне корректно обработать товар без изображений.
- Не использовать `src/prepare/` напрямую.
- Добавить тесты для товара с изображением и без изображения.

## C008. Кнопка покупки на странице товара до реализации корзины

Связанный этап: этап 7 — страница товара.

### Факт по текущему roadmap

Этап 7 реализует детальную страницу товара, но корзина реализуется только на этапе 8.

Поэтому на этапе 7 нельзя добавлять активную POST-форму покупки без backend-логики корзины.

- не выполнять POST-запросы на добавление товара в корзину;
- не создавать временную frontend-корзину;
- активную форму добавления товара в корзину реализовывать только на этапе 8.

### Что изменилось по конфликту

Предыдущий конфликт между скрытой кнопкой, disabled-кнопкой и временной frontend-симуляцией закрыт.

На этапе 7 показываем будущую точку действия, но не реализуем покупку.

### Что остаётся сделать в реализации

## C009. Отзывы и рейтинг на странице товара до реализации review service

Статус: решён.

Связанный этап: этап 7 — страница товара.

Связанный ADR: `docs/decisions/0011-reviews-rating.md`.

### Факт по текущему коду

Модель `Review` уже есть и содержит поле `status`.

Публичный статус отзыва:

```text
Review.Status.PUBLISHED
```

Полноценный review service, форма создания отзыва и проверка покупки относятся к более позднему этапу.

### Принятое решение

ADR 0011 фиксирует:

- на этапе 7 показывать только read-only опубликованные отзывы;
- средний рейтинг считать только по опубликованным отзывам;
- количество отзывов считать только по опубликованным отзывам;
- форму создания отзыва на этапе 7 не добавлять;
- не показывать отзывы в статусах `draft`, `pending`, `rejected`, `hidden` и любых будущих непубличных статусах;
- состояние без отзывов должно отображаться корректно.

### Что изменилось по конфликту

Предыдущий конфликт между read-only отзывами, полным скрытием отзывов и преждевременной формой создания закрыт.

На этапе 7 отзывы используются только на чтение.

### Что остаётся сделать в реализации

- В selector/view детальной страницы получить отзывы по `status=Review.Status.PUBLISHED`.
- Посчитать средний рейтинг по опубликованным отзывам.
- Посчитать количество опубликованных отзывов.
- Добавить read-only блок отзывов в шаблон.
- Не добавлять форму создания отзыва.
- Покрыть публичные и непубличные отзывы тестами.


## C010. Правило похожих товаров на странице товара

Статус: решён.

Связанный этап: этап 7 — страница товара.

Связанный ADR: `docs/decisions/0012-rule-product.md`.

### Факт по текущему коду

В текущей модели каталога нет тегов, брендов, атрибутов, просмотров и полноценной рекомендательной системы.

Для минимальной выборки уже доступны:

- `Product.category`;
- `Product.is_active`;
- `Product.is_deleted`;
- `Product.stock_quantity`;
- `Category.is_active`.

### Принятое решение

ADR 0012 фиксирует:

- похожие товары выбираются только из той же категории;
- текущий товар исключается;
- в блок попадают только активные неудалённые товары;
- категория похожих товаров должна быть активной;
- максимум отображается 3 товара;
- товары с `stock_quantity = 0` можно показывать, но с состоянием `Нет в наличии`;
- подбор по цене, тегам, брендам, популярности, заказам и просмотрам на этапе 7 не реализуется.

### Что изменилось по конфликту

Предыдущий конфликт между простой категорией, близкой ценой и рекомендательной логикой закрыт.

На этапе 7 используется минимальное правило похожих товаров по категории.

### Что остаётся сделать в реализации

- Добавить selector похожих товаров.
- Исключить текущий товар из результата.
- Ограничить результат 3 товарами.
- Отфильтровать неактивные и soft-deleted товары.
- Проверять активность категории.
- Покрыть правило похожих товаров тестами.

## C011. Web-маршруты и HTTP-контракт корзины

Статус: решён и реализован.

Связанный этап: этап 8 — корзина.

Связанный ADR: `docs/decisions/0013-cart-web-routes.md`.

### Принятое решение

Для web-интерфейса корзины используются отдельные маршруты действий с передачей `product_id` в URL:

- `GET /cart/` — просмотр корзины;
- `POST /cart/add/<int:product_id>/` — добавление товара;
- `POST /cart/update/<int:product_id>/` — изменение количества;
- `POST /cart/remove/<int:product_id>/` — удаление позиции;
- `POST /cart/clear/` — очистка корзины.

Все операции изменения состояния выполняются только через `POST`. После успешного `POST` выполняется redirect на `/cart/`.

## C014. Политика количества товара: add, update и merge

Статус: решён и реализован.

Связанный этап: этап 8 — корзина.

Связанный ADR: `docs/decisions/0016-cart-quantity-policy.md`.

### Принятое решение

Вводится единая политика количества:

- `add_to_cart` увеличивает количество существующей позиции;
- `update_cart_item` заменяет количество позиции;
- `remove_from_cart` удаляет позицию;
- `clear_cart` очищает корзину;
- системный максимум одной позиции: `MAX_CART_ITEM_QUANTITY = 99`.

Для пользовательских операций превышение остатка или системного лимита является ошибкой и не меняет корзину.

Для merge используется безопасное ограничение: `min(db_quantity + session_quantity, product.stock_quantity, MAX_CART_ITEM_QUANTITY)`.

### Состояние реализации

- [x] Добавлен `MAX_CART_ITEM_QUANTITY = 99`.
- [x] Количество проверяется внутри сервисов.
- [x] Корзина не меняется при ошибке пользовательской операции.
- [x] `add`, `update`, превышение остатка, превышение лимита и merge покрыты тестами.

## C015. Недоступные товары и битые product_id в session-cart

Статус: решён и реализован.

Связанный этап: этап 8 — корзина.

Связанный ADR: `docs/decisions/0017-session-cart-invalid-products.md`.

### Принятое решение

Нормализация корзины выполняется в service-layer при построении snapshot.

Из корзины автоматически удаляются позиции, если товар:

- не найден по `product_id`;
- soft-deleted;
- имеет `is_active=False`;
- находится в неактивной или скрытой категории.

Товары с `stock_quantity = 0` остаются видимыми, но помечаются как недоступные для оформления. Если `quantity` больше текущего остатка, количество не обрезается silently при просмотре корзины: позиция остаётся с предупреждением, а checkout должен быть недоступен до явного изменения количества.

### Состояние реализации

- [x] Нормализация snapshot реализована в `apps/cart/services.py`.
- [x] Очистка битых и скрытых позиций сохраняется обратно в session.
- [x] Snapshot возвращает warnings для шаблона.
- [x] Snapshot отражает `has_unavailable_items` и `can_checkout`.
- [x] Edge cases покрыты сервисными тестами.

В проекте уже есть:

- обязательная связь `Order.user`;
- гибридная корзина: session для гостя и БД для авторизованного пользователя;
- сервис merge session-cart в DB-cart;
- бизнес-правило: авторизованный пользователь может оформлять заказ и смотреть свои заказы;
- реализованный личный кабинет, где есть вход, выход, профиль и история заказов.

### Принятое рабочее решение

Этапы 9 и 10 реализуются как один вертикальный срез.

Checkout на текущем MVP доступен только авторизованному пользователю. Гостевой checkout не реализуется, потому что текущая модель `Order` требует `user` и история заказов должна быть привязана к аккаунту.

Поведение:

- гость может собирать корзину в session;
- при переходе к checkout гость должен перейти к входу или регистрации;
- после успешного входа session-cart объединяется с DB-корзиной пользователя;
- заказ создаётся только для авторизованного пользователя;
- пользователь видит только свои заказы;
- `Order.user` не делается nullable;
- отдельная модель гостевого заказа не добавляется.

### Почему отдельный ADR не нужен

Решение следует из уже принятой структуры проекта и текущих моделей:

- `Order.user` обязателен;
- web-аутентификация использует Django session;
- личный кабинет нужен для истории заказов;
- гостевой checkout не был обязательной частью MVP.

Отдельный ADR понадобится только если позже будет принято решение разрешить гостевые заказы или отделить заказ от пользователя.

## C017. Контракт checkout-формы и данные доставки

Статус: решён и реализован, отдельный ADR не требуется.

Связанные этапы:

- этап 9 — checkout и заказы;
- этап 10 — пользователи и личный кабинет.

### Факт по текущему коду

Модель `Order` уже хранит snapshot данных покупателя:

- `customer_name`;
- `customer_email`;
- `customer_phone`;
- `delivery_address`;
- `comment`.

Отдельной модели адресов доставки пока нет.

### Принятое рабочее решение

Checkout-форма использует только поля, которые уже есть в `Order`.

Обязательные поля:

- `customer_name`;
- `customer_email`;
- `customer_phone`;
- `delivery_address`.

Необязательное поле:

- `comment`.

Допустимо предзаполнять `customer_name` и `customer_email` из текущего пользователя, если эти данные доступны. Пользователь всё равно подтверждает snapshot-данные в форме checkout.

На объединённом этапе 9-10 не добавляются:

- отдельная модель адресов доставки;
- адресная книга пользователя;
- сложный профиль доставки;
- выбор сохранённого адреса.

### Почему отдельный ADR не нужен

Это не меняет архитектуру и не требует миграций: контракт формы напрямую следует из уже существующей модели `Order`.

Отдельный ADR понадобится, если появится решение хранить несколько адресов доставки или переиспользовать адреса между заказами.

## C018. Граница ответственности между cart service и orders service

Статус: решён и реализован, отдельный ADR не требуется.

Связанные этапы:

- этап 9 — checkout и заказы;
- этап 10 — пользователи и личный кабинет.

### Факт по текущему коду

Сервис корзины уже предоставляет:

- `get_cart_snapshot(request)`;
- `clear_cart(request)`;
- `CartSnapshot.can_checkout`;
- нормализацию недоступных позиций;
- единые правила расчёта количества и стоимости.

### Принятое рабочее решение

`orders.services` не должен читать session напрямую и не должен дублировать правила корзины.

Граница ответственности:

- `cart.services` отвечает за чтение, нормализацию и очистку корзины;
- `orders.services` отвечает за атомарное создание заказа, позиций заказа, уменьшение остатков и создание mock-платежа;
- view остаётся HTTP-слоем: проверяет авторизацию, валидирует форму, получает snapshot корзины, вызывает сервис заказа, ставит messages и делает redirect.

Публичный контракт для этапа 9-10:

```python
create_order_from_cart(
    *,
    user,
    cart_snapshot,
    shipping_data,
)
```

`orders.services` принимает `CartSnapshot`, но внутри транзакции повторно блокирует и перечитывает товары через `select_for_update()`. Snapshot используется как пользовательски подтверждённый состав корзины, а не как единственный источник складских остатков.

Очистка корзины выполняется только после успешного создания заказа.

### Почему отдельный ADR не нужен

Это уточнение уже принятого ADR 0004 и ADR 0014:

- заказ создаётся в service-layer;
- корзина имеет отдельный service-layer;
- checkout не должен читать внутренний формат session-cart.

## C019. Mock-платёж и статусы после checkout

Статус: решён и реализован, отдельный ADR не требуется.

Связанные документы:

- `docs/decisions/0008-payment-order.md`;
- `docs/decisions/0004-order-transaction.md`.

### Факт по текущему коду

В `Order` есть статусы:

- `new`;
- `paid`;
- `processing`;
- `shipped`;
- `completed`;
- `cancelled`.

В `Payment` есть статусы:

- `pending`;
- `succeeded`;
- `failed`;
- `cancelled`;
- `refunded`.

ADR 0008 уже разрешает несколько платежей на один заказ и допускает mock-оплату.

### Принятое рабочее решение

Для MVP checkout сразу создаёт успешный mock-платёж.

После успешного checkout:

- создаётся `Order`;
- создаются `OrderItem`;
- уменьшаются остатки товаров;
- создаётся `Payment` со статусом `succeeded`;
- заказ получает статус `paid`;
- для платежа заполняется `provider = "mock"`;
- сумма платежа равна `Order.total_price`;
- корзина очищается.

Запрет повторной успешной оплаты остаётся бизнес-правилом payment/checkout service. В рамках первичного checkout повторная успешная оплата не возникает, потому что заказ создаётся один раз из корзины.

### Почему отдельный ADR не нужен

Это конкретизация уже принятого ADR 0008 для MVP. Нового архитектурного выбора нет: реальная платёжная интеграция не реализуется, а mock-оплата уже допустима.

## C020. Поведение checkout при изменении остатков во время оформления

Статус: решён и реализован, отдельный ADR не требуется.

Связанные документы:

- `docs/decisions/0004-order-transaction.md`;
- `docs/decisions/0017-session-cart-invalid-products.md`.

### Факт по текущему коду

Корзина уже умеет показывать `can_checkout=False`, если товар недоступен или количество превышает остаток.

ADR 0004 требует:

- `transaction.atomic()`;
- `select_for_update()`;
- повторную проверку остатков при checkout.

### Принятое рабочее решение

Checkout работает по правилу all-or-nothing.

Если во время оформления заказа остатки изменились:

- заказ не создаётся;
- позиции заказа не создаются;
- остатки не уменьшаются;
- mock-платёж не создаётся;
- корзина не очищается;
- пользователь возвращается к корзине или checkout-форме с понятной ошибкой.

Checkout не должен автоматически уменьшать количество товара и не должен создавать частичный заказ по оставшимся позициям. Пользователь должен явно подтвердить новый состав корзины.

Для снижения риска deadlock товары внутри транзакции блокируются в стабильном порядке, например по `Product.id`.

### Почему отдельный ADR не нужен

Это прямое следствие ADR 0004 и ADR 0017:

- создание заказа атомарно;
- корзина не резервирует товар;
- финальная проверка остатков выполняется при checkout;
- пользователь не должен получить заказ с неожиданно изменённым составом.

## C021. Какой заказ даёт право оставить отзыв

Статус: решён.

Связанный этап: этап 11 — отзывы.

Связанный ADR: `docs/decisions/0021-review-eligible-order-status.md`.

### Факт по текущему коду

В проекте уже есть:

- `Review.user`;
- `Review.product`;
- `Review.is_verified_purchase`;
- уникальность пары `user + product`;
- статусы заказа `new`, `paid`, `processing`, `shipped`, `completed`, `cancelled`;
- checkout создаёт заказ со статусом `paid`;
- `OrderItem` связывает заказ с купленным товаром.

### Принятое решение

Подтверждённой покупкой для права оставить отзыв считается заказ текущего пользователя, который содержит нужный товар через `OrderItem` и находится в одном из статусов:

- `paid`;
- `processing`;
- `shipped`;
- `completed`.

Статусы `new` и `cancelled` не дают право оставить отзыв.

На этапе 11 `reviews.services` не проверяет `Payment` напрямую: статус `Order` считается агрегированным бизнес-состоянием заказа.

`Review.is_verified_purchase=True` выставляется при создании отзыва, если `user_can_review_product(user, product)` подтвердил покупку через `Order` и `OrderItem`.

### Что изменилось по конфликту

Конфликт закрыт ADR 0021. Реализация этапа 11 должна опираться на это правило и покрыть его service-тестами.

## C022. Где и как пользователь создаёт отзыв в web-интерфейсе

Статус: решён.

Связанный этап: этап 11 — отзывы.

Связанный ADR: `docs/decisions/0022-review-web-create-contract.md`.

### Факт по текущему коду

Детальная страница товара уже показывает read-only блок опубликованных отзывов и рейтинг.

Формы создания отзыва сейчас нет. В `Review` уже есть поля:

- `rating`;
- `title`;
- `text`;
- `status`;
- `is_verified_purchase`.

### Принятое решение

Форма создания отзыва может отображаться на детальной странице товара `/products/<slug>/`, но создание отзыва обрабатывает приложение `reviews`, а не `catalog`.

Канонический POST-маршрут:

```text
POST /reviews/products/<slug>/add/
```

`catalog` отвечает за отображение товара, опубликованных отзывов и формы или уведомления. `reviews` отвечает за HTTP-обработчик создания отзыва, форму, сервисы, проверку права и redirect после обработки.

После успешного создания пользователь возвращается на страницу товара, предпочтительно к блоку отзывов `/products/<slug>/#reviews`.

### Что изменилось по конфликту

Конфликт закрыт ADR 0022. Реализация этапа 11 должна добавить `reviews/forms.py`, `reviews/services.py`, `reviews/views.py`, `reviews/urls.py` и связать форму на странице товара с namespace `reviews`.

## C023. Начальный статус и видимость нового отзыва

Статус: решён текущей моделью и бизнес-правилами, отдельный ADR не требуется.

Связанный этап: этап 11 — отзывы.

### Факт по текущему коду

`Review.status` по умолчанию равен `pending`.

Публичная детальная страница товара показывает только отзывы со статусом `published`.

В админке уже есть actions публикации, отклонения и скрытия отзывов.

### Принятое рабочее решение

Новый отзыв после создания получает статус `pending` и не появляется публично до модерации.

Пользователю после отправки нужно показать сообщение, что отзыв отправлен на модерацию.

### Почему отдельный ADR не нужен

Решение уже следует из модели `Review`, текущего read-only блока отзывов и правил модерации.
